# 05 证据收集：目录、命名、隐私与"客观证据"

证据决定 petition 能写什么。顺序是：先有证据和事实记录，再写论证。本指南说明证据如何从私有原件变成可上传的展品，如何保存网页证据，如何处理翻译，以及什么样的证据才算 objective evidence。

## 一、三层目录与登记表

```text
cases/<id>/
├── source_documents/<series>/   私有原件与公开来源的保存版本（Git 忽略）
├── evidence/_pending/<series>/  已整理但仍有未关闭关口的候选（Git 忽略）
├── evidence/<series>/           递交用展品（Git 忽略；在登记表中登记）
├── private/                     表格字段映射、签字件、身份号码（Git 忽略）
└── data/exhibit_registry.json   展品 ID、标题、顺序、文件路径（Git 跟踪）
```

| 层级 | 作用 | 进入下一层的条件 |
| --- | --- | --- |
| `source_documents/` | 原件（扫描件、官方 PDF、网页存档），不修改 | 已记录来源、获取日期、SHA-256 |
| `evidence/_pending/` | 规范化后的候选（裁剪、合并、加封面） | 翻译、佐证或事实核对仍未完成 |
| `evidence/<series>/` | 递交展品，只有这一层可以被 petition 引用 | 全部关口关闭，见下方"启用条件" |
| 登记表 | 展品 ID 的唯一来源 | 每个 ID 至少被一份递交文件引用一次 |

**启用条件**（从 pending 移到 evidence）：

1. 与 petition、CV、personal statement、questionnaire 的事实一致；
2. 外文内容（包括印章、批注、证书编号）有完整的认证翻译；
3. 有足够的独立背景说明这份文件证明什么；
4. 证明目的写得窄而准确（写在展品封面上）；
5. 登记表、展品索引、引用检查全部通过（`make check`）。

## 二、展品编号与命名

展品分类（与 case-template 一致）：

| 系列 | 内容 | 示例 ID |
| --- | --- | --- |
| A | 身份与状态 | A-1 护照，A-2 身份文件，A-3 I-94 |
| B | 学位 | B-1 学位证，B-2 成绩单，B-3 学历评估 |
| C | 工作 | C-1 现雇主证明，C-2 过往雇主证明 |
| D | 论文与引用 | D-1 至 D-4 |
| E | 采用与影响 | E-1 至 E-3 |
| F | 同行评审 | F-1 |
| G | 国家重要性背景 | G-1、G-2 |
| H | 申请人陈述与简历 | H-1 endeavor statement，H-2 personal statement，H-3 CV |
| I | 推荐信 | I-1 独立专家，I-2 合作者，I-3 用户/业界 |
| J | 奖项 | J-1 |

命名规则：

- 文件名以展品 ID 开头：`D-1_Example_Paper_and_Preprint_Record.pdf`。
- 同一展品的多个来源用小写字母后缀：`J-1a`、`J-1b`。
- ID 后只用 ASCII 字母、数字、下划线。
- 原件以 `_original` 结尾；公开来源存档以 `_official`、`_source` 或 `_sanitized` 结尾；未完成翻译的候选以 `_untranslated.pdf` 结尾。
- 已用过的 ID 不得复用于备份材料。递交后新增的证据（例如 RFE）使用新的系列，不重用已递交 ID。

## 三、隐私边界

| 可以进 Git | 只能放在忽略目录 |
| --- | --- |
| 日期、类别、收据号 | A-number、SEVIS ID、护照/签证/I-94 号码 |
| 起草文本、登记表、清单 | 出生日期、住址、电话、邮箱 |
| 经审核的脱敏 JSON | 工资、税表、工资单、银行信息 |
| 构建脚本、测试 | 签字件、认证翻译、身份文件扫描 |

规则：

- 不要把身份、移民文件上传到第三方服务（在线 OCR、翻译网站、AI 聊天工具）。
- 身份文件的临时渲染图读完即删。
- 任何 PDF 要进入 Git 前，先检查可见页面、可提取文本层和元数据（作者、标题、软件信息可能泄露姓名或路径）。
- 雇主证明优先申请"不含工资"的版本作为 C-1；含工资版本留作 RFE 备份。
- 不递交雇主保密信息：内部代码、截图、内部指标、内部项目名。

## 四、网页证据的采集方法

网页会变，指标会涨落。RFE 可能在递交数月后到来，届时只有当时的快照能说明"递交时网页写了什么"。

| 步骤 | 做法 |
| --- | --- |
| 1. 打印为 PDF | 浏览器"打印 → 另存为 PDF"，勾选页眉页脚，使 URL 和打印时间出现在每页 |
| 2. 整页截图 | 对动态内容（计数器、图表）补充整页截图；截图需能看到 URL 栏和日期 |
| 3. 第三方存档 | 在 Wayback Machine（web.archive.org）提交保存，记录存档 URL |
| 4. 记录元数据 | URL、获取日期与时间（含时区）、指标口径（统计的是什么）、SHA-256 |
| 5. 每个来源单独日期 | 不同平台在不同日期刷新时，分别标注各自的快照日期，不要强行统一 |
| 6. 递交前刷新 | 递交前约 7 天内刷新所有公开指标，并重建受影响的展品 |
| 7. 递交后不覆盖 | 已递交快照不可修改；递交后新数据另存并标注真实日期 |

需要特别注意的口径：

- **不同平台的计数不能相加**（Google Scholar、Semantic Scholar、GitHub 各自独立），分别报告并注明来源。
- **引用不等于使用**。引用只说明知晓；"采用"需要第三方实现、集成、部署、复现或在其基础上开发的记录。逐条阅读引用文献，分类为"仅提及 / 讨论 / 实验对比 / 复用组件 / 直接使用"。
- 标注作者重叠和自引。
- star、fork、下载量是关注度，不是采用；不要把下载量说成用户数、安装数或机构数。
- 未合并的 pull request 不能写成已合并。
- 需要登录权限才能看到的数据（仓库流量、内部面板）：要么附带有日期的截图 + 申请人关于采集方法的声明，要么不用。

## 五、翻译

依据：8 CFR 103.2(b)(3)。每份外文文件需要完整英文翻译和译者证明。

| 要求 | 说明 |
| --- | --- |
| 完整 | 包括印章、钢印、手写批注、证书编号、页眉页脚 |
| 译者证明 | 声明译者有能力翻译、翻译完整准确 |
| 译者信息 | 打印姓名、签名、日期、联系方式 |
| 不要自译自证 | 尽量由申请人以外的合格译者签署 |
| 名称一致 | 学校、奖项、主办方名称在所有展品中译法一致 |
| 一体化 | 原件 + 译文 + 证明合并为同一展品的一个 PDF |

流程要点：

1. 先冻结（记录 SHA-256）交给译者的准备稿；译者核对的就是这个版本。
2. 译者签字后记录签字版的 SHA-256。原件或准备稿任何改动，都需要译者重新核对并签字，不能"绕过去"更新哈希。
3. 签字版必须是**可见签名的扁平 PDF**。带交互签名域的 PDF 在去除表单字段或扁平化时可能丢失签名，先打印扫描或导出扁平副本。
4. 申请人自己加的英文说明不能替代认证翻译。

## 六、什么才算"客观证据"

officer 会区分"申请人自己说的"和"第三方独立产生、可核实的"。按证明力大致排序：

| 证明力 | 类型 | 例子 |
| --- | --- | --- |
| 高 | 第三方独立产生、带日期、可公开核实 | 官方录用决定、学校出具的证明、他人论文中实际使用你方法的实验段落、官方奖项名单 |
| 中高 | 第三方签署的第一手事实信 | 用户说明在什么项目中如何使用了你的工具；合作者确认你的具体分工 |
| 中 | 平台记录 | commit 历史、PR、贡献者统计、引用列表（附口径说明） |
| 低 | 申请人自制材料 | 自己的截图、项目介绍、自述影响 |
| 很低 | 空泛的推荐信、行业综述 | 只讲行业需要、只有赞美而无具体事实 |

写证据时的检查问题：

- 这份文件是谁产生的？与申请人是否独立？
- 它证明的是"领域重要"还是"本 endeavor 的影响"？
- 是否有日期、来源、可核实路径？
- 有哪些局限？在展品封面或 D/E 系列报告中如实写出局限，比被 officer 发现更好。
- 无法核实的量化主张（例如雇主内部的收入、延迟、故障率提升）一律不写，改为定性描述。
