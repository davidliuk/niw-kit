# 03 写 Petition：案件理论、Endeavor 与各部分写法

本篇讲怎样从证据出发写出 Petition Letter（`case-template/workproduct/01_Petition_Letter.md`）以及配套的 H-1、H-2、Officer Roadmap 和 Exhibit Index。模板里的 `<!-- GUIDE: ... -->` 注释给出逐段写法，本篇讲整体方法和顺序。

> 本篇不是法律意见。法律依据以 INA 203(b)(2)、8 CFR 204.5(k)、*Matter of Dhanasar*, 26 I&N Dec. 884 (AAO 2016) 和 USCIS Policy Manual Vol. 6, Part F, Ch. 5 为准；Policy Manual 会更新，动笔前在 uscis.gov 上重读一遍，并记下核对日期。

## 1. 写作顺序

不要从 Petition 开头写起。按下面的顺序：

| 步骤 | 产出 | 为什么 |
| --- | --- | --- |
| 1 | 证据清单与 exhibit registry | 先知道手里有什么，再决定说什么 |
| 2 | `06_Claim_Evidence_Ledger.md` 初稿 | 每个要写的事实先找到能证明它的那页纸 |
| 3 | 一句话 Endeavor（锁进 `case.json`） | 后面所有文件都围绕它 |
| 4 | H-1 Proposed Endeavor Statement | 计划决定了 Prong 1 的"未来输出"和 Prong 2 的"plan" |
| 5 | Petition 第 IV–VII 部分 | 先写论证主体 |
| 6 | Petition 第 I 部分 Summary 和开头 | 主体定了再写摘要 |
| 7 | H-2 Personal Statement | 与 Petition 对齐分工和事实 |
| 8 | Officer Roadmap、Exhibit Index 矩阵 | 最后按定稿的论证挑最强证据 |
| 9 | 全部文件跑 ledger 复核和 `make check` | 数字、日期、角色、Endeavor 句子必须处处一致 |

## 2. 先定案件理论（case theory）

案件理论是一段话：**谁，解决什么具体问题，用什么方法，已经有谁在用，下一步交付什么，给谁用。** 写不出这段话，Petition 一定散。

检验标准：把这段话给一个不懂你领域的人看，他能复述出"这个人做的东西和别人做的有什么不一样、谁已经在用"。

常见失败：案件理论其实是"这个领域很重要，我在这个领域工作"。这样的理论只能证明领域重要，撑不起 national importance。

## 3. 一句话 Endeavor

Endeavor 是整个案子的锚。递交后不能改（*Matter of Izummi*, 22 I&N Dec. 169 (Assoc. Comm'r 1998)）；RFE 回复只能解释，不能重新定义。

**大小要合适：**

| 问题 | 例子（虚构） | 官员会怎么说 |
| --- | --- | --- |
| 太大，等于领域 | "推动人工智能安全发展" | 证据只证明领域重要，不证明你的 endeavor 重要 |
| 太小，等于工作 | "优化我司广告系统的延迟" | 受益者只有一个雇主 |
| 合适 | "开发并开源用于检测公共卫生数据管道中 schema 漂移的验证工具，并与州级数据团队一起评估" | 有具体问题、具体方法、具体产出、具体用户 |

**结构：** 动词（develop / evaluate / disseminate）+ 具体技术对象 + 方法特征 + 产出形式 + 使用场景。

**与雇主的关系：** 如果 endeavor 和本职工作相关，要把雇主写成"验证场景"而不是"受益者"，产出必须公开（开源、论文、benchmark）。递交前确认雇主的 IP 和兼职/外部活动政策允许这些公开工作。

## 4. 各部分怎么写

### 4.1 开头两页

官员认真读的通常只有前两页。前两页必须出现：

1. 一句话 endeavor；
2. 申请人最强的个人成果（具体角色 + 可核实的结果）；
3. **别人已经在用这项工作**的最强证据；
4. 三个 prong 各一句结论，每句带引用。

法律标准放后面，写短。

### 4.2 EB-2 门槛

- 美国硕士及以上：成绩单 + 学位证即可（B-1、B-2）。
- 外国学位：加学历认证（B-3）；三年制学士要谨慎，考虑"学士 + 五年递进经验"路线（8 CFR 204.5(k)(2)、(k)(3)(i)），用经历信证明日期、全职和职责递进。
- 职业要选与 **endeavor** 对应的职业，不一定是现在的 job title，用一句话说明二者关系。

### 4.3 Prong 1：Substantial Merit

通常最容易。写问题、现有方法的不足、你的工作测到了什么。结果写清来源和条件："论文在 X benchmark、Y 配置下报告了 Z（Exhibit D-1 第 4 页）"。

### 4.4 Prong 1：National Importance（最容易失败）

按这个顺序写，每一块都要有证据：

1. **与现有工作的区别。** 点名两三种主流方法，用平实英文说明你的方法多做了什么，以及论文里测出的差距。然后证明"别人也认为它不同"：后续论文把它当 baseline、综述把它单独归类、独立专家信解释差别。不要写 "first" 或 "only"，除非有来源这么说。
2. **别人已经在用（adoption table）。** 把最强的 3–8 条使用记录做成表格**直接放进 Petition 正文**：谁（机构、性质、国家）、与申请人的关系、具体做了什么、证据页码。使用类型用固定词汇，从强到弱：部署/集成 > 运行了发布的代码 > 基于其输出或以其为基础 > 按论文复现 > 作为 baseline 比较 > 综述讨论 > 仅引用。**绝不升级**：引用不是使用，比较不是采用。
3. **未来产出的更广影响。** 把 H-1 的下一步产出接到具体用户群上："已经在用 X 的这些团队，会用 Y 来……"。
4. **政府或权威背景。** 一段话即可。选点名了你所解决的具体问题的来源（机构计划、标准工作、资助公告），引原句、注明抓取日期、说明哪项产出对应它。不要暗示机构背书。

### 4.5 Prong 2：Well Positioned

Policy Manual 列出的因素：教育、技能、知识；相关工作的成功记录；未来计划；已有进展；潜在用户、投资者或其他相关方的兴趣。逐项用文件回答：

| 因素 | 用什么证明 | 注意 |
| --- | --- | --- |
| 个人角色 | H-2 个人陈述 + I-2 合作者信 + 客观记录（作者顺序、贡献标注、commit 历史） | 多作者论文本身只证明"共同作者" |
| 引用 | D-3 引用报告 + D-4 显示使用的引用文献 | 把引用拆成"用了"和"只引用"，注明快照日期和排除自引规则 |
| 计划 | H-1 首年按季度的交付物表 | "继续研究 X"不是计划 |
| 进展 | 已开始的代码、协议草稿、递交后的新成果（RFE 时注明日期） | — |
| 合作 | 合作者亲自写的信 | 只有申请人自己说不算 |
| 资源 | 成本表 + 谁付 + 非金钱支持（实验室算力、共享设施） | 资金不是 Dhanasar 要件，但不写就会被当作缺口 |
| 兴趣 | 别人**做了**什么：运行代码、提 issue/PR、邀请报告、写信说明使用 | 自荐的角色不能写成"受邀" |
| 审稿、奖项 | F-1、J-1 | 只作辅助；写清邀请来源和获奖层级 |

### 4.6 Prong 3：Balance

Dhanasar 列出的因素各用一个小标题回答：

1. **劳工证或工作 offer 是否不现实。** 诚实的写法通常是：劳工证测试的是某个雇主的某个职位和招聘，无法衡量被多个机构同时使用的公开产出，也无法覆盖申请人独立设定的研究议程。已经有 offer 的，不要说拿 offer 不现实。
2. **即使有合格的美国工人，美国是否仍受益。** 申请人特有、增量的贡献：原始方法和基础设施由申请人建立，别人已在使用，申请人最能把它推进到下一版公开发布；这些产出增强美国研究者和工程师的能力。
3. **紧迫性。** 要具体：领域按月迭代（有日期的后续工作为证）、某项政府计划正在进行、用户依赖持续维护的版本。

**不用的因素也要写一句"不依赖此因素"**，否则官员会把它列为未满足。**永远不要**主张劳动力短缺、"没有美国人能做"或"不可替代"。STEM 高学位是 Policy Manual 中的正面因素，只作辅助，学位层级如实写。

## 5. H-1、H-2、Roadmap、Index 的分工

| 文件 | 任务 | 不要做 |
| --- | --- | --- |
| H-1 Proposed Endeavor | 定义 endeavor、问题、过去→未来对照表、受益者、资源、按季度的首年计划 | 写成第二份 Petition |
| H-2 Personal Statement | 申请人怎样发现问题、每项工作中申请人的具体分工、发布后别人怎么用以及这怎样塑造了下一个问题、为什么在美国继续 | 写成散文版 CV 或自夸 |
| 04 Officer Roadmap | 一页：每个要件 → 一个命题 → 两三份最快的证据和页码 | 写论证 |
| 05 Exhibit Index | 证据矩阵（"证据显示什么"）+ 自动生成的分系列表格 | 写"这不能证明什么" |
| 06 Ledger（不递交） | 每句事实 → 主证据 → 佐证 → 证据边界 → 剩余风险 | 递交它 |

## 6. 语气

- 用准确的主语和动词肯定地陈述证据显示了什么："The paper reports…"、"The repository records…"、"Group X ran the released code on…"。
- 不要在递交文件里堆"这不是采用""这不是独立复现"之类的自我限定，那等于在官员看材料前先认输；限定放进私有 ledger，递交文件只写在限定范围内成立的话。
- 但也绝不夸大。被官员发现的一处夸大会拖累附近所有的论证。
- 每个数字带快照日期和来源。每个事实句带引用。

## 7. 常见错误

前六条对应 national importance、well positioned、balance 三项中最常见的证据缺口；更完整的清单见 `08_common_weaknesses.md`（常见薄弱点与对策）。

1. **只证明了领域重要。** 证据只说明整个领域重要，却没有说明申请人的工作与正在进行的同类研究有何区别。对策：第 4.4 节第 1 步。
2. **采用证据埋在附件里。** 第三方使用报告只作为单独附件，正文和 Roadmap 都没有指向它，官员可能根本没注意到。对策：adoption table 放进 Petition 正文，Roadmap 里单列一行。
3. **只有合作者的信。** 只讨论领域重要性、概括行业需求或给出结论性陈述的信分量很低；把独立用户信当作"可有可无"是常见失误。对策：见 `04_recommendation_letters.md`，递交前拿到 2–3 封用户的一手事实信。
4. **引用、百分位、审稿没有和具体进展挂钩。** 只报数字，不说明它们对应了哪些具体进展、相关方兴趣、系统集成或更广的技术影响。对策：拆分引用类型，审稿只作辅助。
5. **计划、合作、资源写得虚。** 缺少清晰的未来工作计划、持续合作、已落实的资金或机构支持的证据。对策：季度表 + 合作者信 + 成本表。
6. **Prong 3 只写了一种理由。** 没有逐项说明劳工证为何会限制这项工作、为何申请人的贡献难以在劳工证中表述、为何紧迫。对策：每个因素一个小标题。
7. **Endeavor 在各文件里措辞不一致**，或递交后想改。对策：锁进 `case.json`，`make check` 自动比对。
8. **角色说法互相矛盾**（个人陈述、合作者信、作者顺序、commit 历史）。对策：ledger 第 9 行，定稿前四方对齐。
9. **数字前后不一致**（Petition 和推荐信里同一个指标不同）。对策：ledger 的数字登记表。
10. **把机密信息写进递交材料**（内部系统名、未发布指标、薪资）。对策：只写类别级别的职责。
11. **政策材料堆砌。** 十几份"AI 很重要"的报告不如一份点名你具体问题的政府文件。
12. **把官员当读者之外的人。** 官员不是你领域的专家，每个技术概念第一次出现时先用平实英文解释。

## 8. 递交前自查

- [ ] 前两页出现了 endeavor、最强个人成果、最强第三方使用、三个 prong 结论。
- [ ] Adoption table 在正文里，每行有关系披露和页码，使用类型没有升级。
- [ ] 区别于现有工作的论证有第三方来源支持，而不只是申请人自己说。
- [ ] Prong 2 每个 Policy Manual 因素都有文件对应。
- [ ] Prong 3 每个 Dhanasar 因素都有一段回答（包括"不依赖"）。
- [ ] Endeavor 句子四处一致；所有数字在 ledger 登记表中且处处一致。
- [ ] 所有占位符已替换，`make final` 通过。
- [ ] 时效性内容（费用、表格版本、NIW 所需的劳工证表格、递交渠道）已在 uscis.gov 核对并记下日期。
